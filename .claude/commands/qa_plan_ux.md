# /qa_plan_ux — Browser QA Plan for Cursor

You are a QA engineer who thinks like a real user. Your job is to define browser test scenarios that prove the feature works from a human's perspective. Cursor executes these after `/build`, after `/qa_plan` passes.

Test the experience, not the system. APIs, DB, rules — `/qa_plan` covers that. This plan proves a human can do what the MVP promises.

---

## Where This Sits

```
/roadmap → /ux → /spec → /qa_plan → /qa_plan_ux → /build → run /qa_plan → then run /qa_plan_ux
```

`/qa_plan` generates two files: the QA plan + a shared test data catalog.
`/qa_plan_ux` reads the test data catalog for concrete values and the UX doc for everything else.

---

## Input

```
/qa_plan_ux kyc_mvp_1.1
```
or paste the MVP block directly.

## Step 0: Gather Context

Read in this order:

1. **UX doc** (`ux/[serial]_ux.md`) — PRIMARY input. Wireframes, steps, inputs, failures.
2. **Test data catalog** (`tests/[serial]_test_data.md`) — generated by `/qa_plan`. Concrete values to type and submit.
3. **Spec** (`specs/[serial]_spec.md`) — for understanding what's behind the UI.
4. **MVP block** (`roadmaps/`) — acceptance criteria.
5. **QA plan** (`tests/[serial]_qa_plan.md`) — to avoid overlap.
6. **Prior browser QA plans** — same feature shortcode.

If no UX doc and MVP has a human touchpoint: stop. Say `Run /ux [serial] first.`
If no UX doc and backend-only: stop. Say `[serial] has no UI. Use /qa_plan only.`
If no test data catalog: stop. Say `Run /qa_plan [serial] first. It generates the test data catalog.`

Targeting priority:

  2. Input label or placeholder from wireframe

Only use labels from the UX doc wireframe. Don't invent.

## Step 2: Action Vocabulary

Every step uses exactly one action. Tool-agnostic — Cursor, Playwright, or manual QA maps these to their capabilities.

```
ACTIONS
═══════

NAVIGATION:
  GO TO [url or path]                    — open URL (entry point only)
  CLICK [element]                        — click visible element
  CLICK BACK                             — browser back
  REFRESH                                — full reload
  OPEN NEW TAB [url]                     — new tab
  SWITCH TO TAB [N or "previous"]        — switch tabs

INPUT:
  TYPE [text] INTO [field]               — type into input (clears first)
  CLEAR [field]                          — remove text
  SELECT [option] FROM [dropdown]        — choose from dropdown
  TOGGLE [checkbox/switch]               — flip boolean
  UPLOAD [file description] TO [area]    — attach file
  DRAG [element] TO [target]             — drag and drop

GESTURE:
  HOVER [element]                        — cursor over (tooltips, hover menus)
  LONG PRESS [element]                   — hold ⚠️ MOBILE ONLY
  SWIPE [direction] ON [element]         — swipe ⚠️ MOBILE ONLY

OBSERVATION:
  SEE [element/text]                     — visible on screen
  SEE [element] WITH [text/value]        — shows specific content
  NOT SEE [element/text]                 — NOT visible
  READ [element] → [store as name]       — capture for later
  COUNT [elements] → [expected N]        — verify count
  SEE [element] IS [disabled/enabled/checked] — element state

DIALOG:
  ACCEPT DIALOG                          — OK on browser alert
  DISMISS DIALOG                         — Cancel on browser alert
  SEE DIALOG WITH [text]                 — verify dialog content

WAIT:
  WAIT FOR [element/text]                — until appears (timeout: 10s)
  WAIT FOR [element] TO DISAPPEAR        — until gone
  WAIT [N] SECONDS                       — explicit pause (sparingly)

VIEWPORT:
  SET VIEWPORT [width] x [height]        — change window size
  SCROLL TO [element]                    — scroll into view
  SCROLL DOWN / SCROLL UP                — scroll page

KEYBOARD:
  PRESS [key]                            — single key
  PRESS [modifier+key]                   — combo
  FOCUS [element]                        — keyboard focus without click

STATE:
  STORE [value] AS [name]                — save for later
  COMPARE [current] WITH [stored name]   — verify match
```

Rules:
- **One action per step.**
- **Element refs from UX doc.** `CLICK [Submit]` not `CLICK [.btn-primary]`.
- **Data values from test-data catalog.** `TYPE "Priya Sharma" INTO [Full Name]` where value comes from `valid_kyc_1`.
- **Can't express it? Mark `NEEDS SIMULATION`.**
- **SEE is primary verification.** Invisible checks (DOM, network) belong in `/qa_plan`.

## Step 4: Mandatory Scenarios

### A. Happy Path (from UX doc §2)

```
Source: UX doc §2 steps + flow visual
Dataset: valid_[feature]_1 then valid_[feature]_2
Prove: User walks entire flow → reaches acceptance state.

  - Follow EVERY UX doc step, in order
  - Use wireframe for screen layout
  - Use catalog values for input
  - Last step = MVP acceptance
  - After last step: REFRESH → SEE [data persists]
  - Repeat with dataset 2 (not hardcoded)
```

### B. Input Validation (from UX doc inputs + catalog invalid sets)

```
Source: UX doc inputs + test-data invalid datasets
Prove: Every rule shows correct error in browser.

Per field, per rule:
  SC: [field] — [violation]
    Dataset: invalid_[field]_[type]
    1. Fill form with dataset values
    2. CLICK [Submit]
    3. SEE "[error from catalog's Expected error]"

  SC: [field] — valid clears error
    Dataset: valid_[feature]_1
    1. Fill [field] with valid value
    2. NOT SEE "[error]"
```

### C. Failures (from UX doc §3)

```
Source: UX doc §3
Dataset: valid_[feature]_1 (failure is environmental)
Prove: Each failure → correct message → recovery works.

Per failure:
  SC: [failure name]
    GIVEN: [condition — may need simulation]
    1. Attempt with valid data
    2. SEE "[message from UX doc §3]"
    3. [Recovery from UX doc §3]
    4. No partial state

Mark NEEDS SIMULATION if can't trigger from browser.
```

### D. Duplicate Submission

```
Source: UX doc §2 — any submit button
Dataset: valid_[feature]_1

  SC: double submit
    1. Fill valid data
    2. CLICK [Submit]
    3. CLICK [Submit] again immediately
    4. SEE [Submit] IS [disabled] OR SEE error/same success
    5. Only one result on screen
```

### E. Responsive [ONLY IF UX DOC MENTIONS MOBILE/DEVICES]

```
Source: UX doc §1 environment

  SC: [viewport] happy path
    1. SET VIEWPORT [width] x [height]
    2. Walk happy path at this viewport
    3. SEE [key elements], SCROLL TO before interacting

    Visual issues (overlap, truncation) can't be fully verified via actions.
    Tool supports screenshots → capture each step.
    Otherwise → mark NEEDS VISUAL REVIEW.
```

Skip if UX doc doesn't mention responsive.

### NOT Written

- API tests — `/qa_plan`
- DB checks — `/qa_plan`
- Business rules — `/qa_plan`
- Performance/load
- Spec's "Out of Scope"
- Empty/loading states unless UX doc defines them

## Step 5: Human Behavior Rules

```
REALISM
═══════

Before CLICK/TYPE:
  - SCROLL TO [element] if possibly below fold
  - SEE [element] before acting

Between form fields:
  - PRESS [Tab] to move
  - WAIT [1] SECONDS between fields

After submit:
  - WAIT FOR [loading indicator] TO DISAPPEAR
  - If none defined: WAIT [2] SECONDS

Test data:
  - ALL values from test-data catalog
  - Each scenario uses its declared dataset

On failure:
  - FAIL immediately. No retries.
  - Capture what IS visible (title, headings, errors)

After persistent actions:
  - REFRESH
  - SEE [data just entered]
```

## Rules

1. **UX doc = truth.** Elements, messages, flow from UX doc.
2. **Data from catalog.** Every value from `tests/[serial]_test_data.md`.
3. **One action per step.** Vocabulary only.
4. **Acceptance is final test.** Last happy path step = MVP acceptance.
5. **No overlap with /qa_plan.** No API/DB/rule tests.
6. **Fail fast.** No retries. Capture and fail.
7. **Gaps reported, not filled.**
8. **One plan per MVP.**

## Division: /qa_plan vs /qa_plan_ux

```
                    /qa_plan               /qa_plan_ux
                    ───────               ──────────
Source of truth     Spec                  UX doc
Test data           Generates catalog     Consumes catalog
Proves              System works          Experience works
Tests APIs          YES                   NO
Tests DB            YES                   NO
Tests UI            NO                    YES
Tests validation    Contract-level        User-facing messages
Tests failures      All spec errors       Only UX doc §3
Element targeting   N/A                   Wireframe labels
Human behavior      N/A                   YES
Persistence         DB query              Page refresh
Runs via            Claude Code           Cursor
Runs when           First                 After /qa_plan passes
```

## Coordination

```
TEST DATA:
  /qa_plan generates tests/[serial]_test_data.md
  /qa_plan_ux reads it. Same values everywhere.

EXECUTION:
  1. /qa_plan first (Claude Code)
  2. GATE fails → /qa_plan_ux BLOCKED
  3. /qa_plan passes → /qa_plan_ux runs (Cursor)
  4. Both pass → MVP done

REGRESSION:
  Building 1.2 → run all prior plans for same feature shortcode.
  This prompt = one MVP. Regression = execution concern.
```
